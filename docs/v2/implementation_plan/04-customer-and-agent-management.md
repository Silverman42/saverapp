# Module 04 — Customer and Agent Management

## Summary

Implement Customer and Agent operational records, current assignment scope, registration, profile management, lifecycle controls, directories, notifications, and audit integration in staged work. Authentication remains authoritative for accounts, invitations, credentials, MFA, sessions, and recovery. Roles and Permissions remains authoritative for role capabilities and granular Admin permissions. Financial modules remain authoritative for fees, balances, plans, transactions, requests, settlement, reconciliation, and archival or offboarding obligations.

The Module 04 specification is still a detailed draft. Its proposed product decisions must be confirmed before schema or behavior depending on them is implemented. Staged screens may show an explicit unavailable state for an unfinished dependency, but unavailable data must never be represented as zero, eligible, settled, or successfully transferred.

## Current Baseline

- Laravel 13.32, Fortify 1.39, Inertia Laravel 3.3, Vue 3.7, Wayfinder 0.1, Spatie Laravel Permission 8.3, and Pest 4 are installed.
- `users` stores normalized email, immutable `user_type`, account state, authenticator state, permission version, and authentication data. No Customer or Agent profile, assignment, lifecycle-history, or creation-attempt tables exist yet.
- Modules 01–03 establish fixed user types, closed registration, account-state behavior, mandatory Agent/Admin MFA, direct Admin permission grants, fresh authentication, permission-version refresh, and the central authorization evaluator.
- Module 03 resource scope (`AUTHZ-T07`), Authentication invitation/recovery integration, fee snapshots, canonical notifications, and canonical audit evidence remain incomplete or blocked on owning-module contracts.

## Interface and Ownership Boundaries

- **Profiles and identity:** Module 04 owns Customer and Agent operational profiles linked one-to-one with the existing authentication account. Public Customer/Agent IDs are immutable, non-reused references; authentication email remains on the account boundary.
- **Assignments and scope:** Module 04 owns one versioned effective Customer assignment and its history. Policies, scoped queries, jobs, downloads, and discovery must derive access from the current effective assignment rather than historical interaction or possession of an identifier.
- **Authentication:** Module 02 owns invitation tokens and states, activation, email changes, MFA, sessions, locks, suspension/deactivation mechanics, and recovery. Module 04 requests these operations through purpose-specific integration boundaries and never sets another user's password or authentication secret.
- **Authorization:** Module 03 remains the source of fixed role capabilities and Admin permissions. Every write rechecks the exact permission, account state, operational eligibility, assignment, profile/assignment version, and any required fresh-authentication evidence at commit.
- **Financial dependencies:** Modules 05–10 provide authoritative fee, balance, plan, request, reservation, settlement, reconciliation, and pending-work results. Their contracts must distinguish an authoritative empty result from unavailable or failed evaluation; unknown gates fail closed.
- **Notifications and audit:** Module 04 emits one durable source event for each material operation. Modules 13–14 own delivery, inbox, canonical audit search, retention, and reveal/export policy. Successful notices dispatch only after commit and never substitute for required audit durability.
- **Frontend:** Future pages use Inertia Vue, Wayfinder route functions, existing UI components, dark-mode conventions, and the shared page-header/breadcrumb rules. Frontend visibility is presentational; direct endpoints remain server-authoritative.

## Staged Delivery Rules

- CAM-T01 is a hard product gate. A proposed field, status, workflow, retry policy, or visibility rule is not an implementation default until confirmed.
- CAM-T02 and CAM-T03 establish the minimum safe domain and authorization foundation. No controller may bypass their normalization, eligibility, scope, version, or assignment services with ad hoc queries or direct relationship mutation.
- CAM-T04 may present a working profile/directory shell before financial modules are complete, but unavailable sections must show an explicit unavailable state and cannot expose guessed counts, zero balances, or enabled dependent actions.
- CAM-T05 and CAM-T06 are coordinated vertical slices with Authentication. Customer registration additionally requires an authoritative fee configuration; absence of that contract is not a zero-fee configuration.
- Each mutation task includes its own canonical event, protected-history, notification intent, denial, concurrency, and rollback coverage. CAM-T13 closes the shared cross-module delivery, retrieval, indexing, and failure-management behavior rather than retrofitting missing evidence later.
- Archival, final offboarding, and reassignment cannot report success when any required owning-module gate or handover is unsupported or unavailable.

## Verification Strategy

- Add focused Pest feature tests with each implementation task for successful behavior, validation, authorization, scope isolation, stale versions, concurrency, rollback, privacy, and important dependency failures.
- Test protected endpoints directly as Customer, assigned/unassigned Agent, baseline Admin, authorized Admin, restricted Admin, inactive/suspended/deactivated users, and users whose authority changes before commit.
- Use factories and authoritative fakes or contracts for isolated task coverage; never treat a placeholder service, missing integration, or empty fixture as proof that an obligation is zero or complete.
- Verify Inertia prop omission for private data, Wayfinder navigation/submission, validation feedback, loading/empty/unavailable/revoked states, keyboard/touch behavior, responsive layouts, and light/dark rendering.
- Re-run the narrowest relevant Pest files after each task. Before CAM-T14 completes, run the complete compact PHP suite, PHPStan, frontend checks/type checks/build, applicable diagnostics, and Pint for changed PHP files.
- Maintain an acceptance-evidence matrix covering all 38 `CAM-FR-*` requirements and 57 `CAM-AC-*` scenarios, including fixture/authority context and audit/notification references where applicable.

## Assumptions and Deferred Decisions

- Confirmed decisions from Modules 01–03 remain binding. Proposed decisions in Module 04 Section 18 remain pending until CAM-T01 records explicit approval or revision.
- The application remains single-business with fixed Customer, Agent, and Admin roles. No public registration, role conversion, bulk operations, scheduled transitions, permanent deletion, or multi-Agent Customer assignment is introduced.
- Operational profile status remains independent from authentication account state. A lifecycle action cannot implicitly activate, suspend, recover, or change credentials unless it invokes the authorized Authentication workflow explicitly required by the specification.
- Module 04 preserves financial history and original actors. It does not calculate fees, post transactions, infer settlement, replace reconciliation, or invent approval authority.
- Detailed notification retention/preferences and audit retention/reveal/export remain with Modules 13–14. Module 04 retains no manual purge or unrestricted sensitive-history endpoint.
